Learning Backend For Real (Not Just Copy-Pasting Tutorials)

personal field note · by Vinayak Mishra

A few months ago "server" and "console" were just words I typed without really understanding. Here's what actually changed, what finally clicked, and the Spotify-style backend I built while figuring it out.

What A Server Actually Is

For the longest time I thought of "the backend" as some vague cloud thing that just happens. What actually clicked was simpler than I expected: a server is just a program running somewhere, sitting and waiting, listening on a port for someone to send it a request. That's it. No magic — just code that never stops running, constantly checking "did someone ask me for something?"

The browser, on the other hand, doesn't know anything on its own. It sends a request out into the internet — "hey, give me this data" — and just waits. It has no memory of your database, no idea what a user's password hash looks like, no access to anything private. That separation is the entire reason backend exists: the browser is public and exposed, the server is where the actual logic and secrets live.

The Console Finally Made Sense

I used console.log() for months without really understanding what I was looking at. The console isn't just "print stuff to check if it works" — it's the closest thing to a conversation with your own code while it's running. On the frontend, the browser console shows you what's happening in the user's browser, in real time, as they click and scroll. On the backend, the terminal running your server shows what's happening on the server side — requests coming in, database queries, errors before they ever reach a user.

Once I stopped treating the console as a debugging afterthought and started treating it as the primary way to actually see what my code is doing step by step, backend logic stopped feeling like a black box.

Where I Actually Am Right Now

Phase 1 JavaScript + Node.js Modules Done
Phase 2 Express.js + Middleware + JWT Done
Phase 3 MongoDB + Mongoose In Progress
Phase 4 Bcrypt + Refresh Tokens Next Up

Phase 1 and 2 stopped being theory once I actually built something with them — writing my own middleware, seeing a JWT get generated and verified on a real request instead of just reading about how JWTs work in a blog post. Phase 3 is where I am now: not stuck, just still tightening how I structure schemas and relationships properly instead of hacking things together until they work. Phase 4 — proper password hashing and refresh token rotation — is next, and honestly the part I'm most looking forward to, because it's where "it works" turns into "it's actually secure."

Building A Spotify-Style Backend To Actually Test All This

Reading about auth and middleware is one thing. Building an API where none of it is optional is another. So I built a Spotify-style backend — a real RESTful API for a music platform, with separate flows for a regular listener and an artist account, because those two roles need genuinely different permissions, not just a different UI on top of the same data.

🎵 spotify-backend — full source on GitHub view repo →

The stack ended up being Node.js + Express on top, MongoDB with Mongoose for data, JWT for authentication, and bcrypt for password hashing. Nothing exotic — the goal wasn't to use every tool, it was to actually understand every tool I used.

  • signup / login with JWT-based authentication
  • protected routes gated behind custom auth middleware
  • full CRUD for songs — artists can add and manage tracks
  • playlist creation and management for regular users
  • separate permission logic so an artist account and a listener account can't do the same things
  • user profile management tied to the authenticated session

The middleware part is what actually taught me the most. Writing a function that sits between the request and the route handler — checking the token, deciding whether this request is even allowed to continue — made "authentication" stop being an abstract concept and start being a piece of code I had written and could point to.

What's Still Rough

I'm not going to pretend this is finished. The Mongoose schemas need cleaner relationships between users, artists, songs, and playlists instead of some of the workarounds I used to get things working fast. And right now, tokens don't refresh — once they expire, that's it, log in again. Phase 4 fixes exactly that: proper bcrypt-hashed passwords everywhere and refresh tokens so sessions don't just die without warning.

That's the honest state of it. Not a finished product — a working one, with a clear list of what's next.
